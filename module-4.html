프롬프트 평가(Eval)와 자동 채점

“좋아진 것 같다”를 숫자와 근거로 바꾸는 모듈입니다. 골든셋을 만들고, judge를 설계하고, 사람 채점과 얼마나 맞는지 확인한 뒤, 8천 건을 안정적으로 돌립니다.

13레슨 약 100분 선행: 모듈 1 근거: claude-cookbooks evals · courses
이 모듈의 한 문장

평가 없이 프롬프트를 고치는 것은, 눈 감고 사진 보정하는 것과 같습니다. 감이 나쁘다는 게 아니라, 무엇이 좋아졌는지 말할 수 없다는 게 문제입니다. 8천 문항 규모에서는 그 “말할 수 없음”이 곧 사고입니다.

4.1 바이브 평가의 함정

프롬프트를 고치고 결과를 두세 개 읽어 보고 “더 좋아졌네”라고 넘어가는 것을 바이브 평가라 부릅니다. 세 가지 이유로 반드시 실패합니다.

  1. 표본이 편향됩니다. 사람은 재미있는 사례·명백한 사례를 고릅니다. 어려운 경계 사례는 안 봅니다.
  2. 기억이 흐려집니다. 어제 결과와 오늘 결과를 나란히 비교하지 않으면, 차이는 느낌으로만 남습니다.
  3. 개선과 퇴보가 같이 옵니다. 환각을 줄이면 답이 짧아지고, 짧아지면 누락이 늘어납니다. 한쪽만 보면 속습니다.

실제로 자주 일어나는 일을 표로 보면 이렇습니다.

변경좋아진 것나빠진 것(안 보임)
“짧게 쓰라” 추가읽기 편해짐채점 근거 문장이 사라져 부분점수 판정 불가
temperature 0형식 안정표현이 단조로워져 해설이 템플릿처럼 됨
k=3으로 축소비용·지연 감소recall 하락 — 두 문서를 종합해야 하는 문항에서 실패
요약 인덱싱긴 청크 검색 개선용어가 바뀌어 특정 키워드 검색이 죽음

그래서 필요한 것은 딱 두 가지입니다. 고정된 문제집(골든셋)과 같은 자로 재는 도구(채점기)입니다. 이 두 개만 있으면 프롬프트를 바꿀 때마다 30초 만에 “좋아졌는지” 알 수 있습니다.

4.2 eval의 4요소와 데이터셋 만들기

평가는 네 부분으로 이루어집니다. 이 구분이 명확해야 “어디가 문제인지” 말할 수 있습니다.

입력
모델에 들어가는 것. 문항 + 학생 응답 + 루브릭.
출력
모델이 낸 것. 우리 코드가 파싱한 구조까지 포함.
골든 정답
정답 자체일 수도 있고, “무엇을 보면 맞는지”에 대한 설명일 수도 있습니다. 채점에서는 후자가 더 유용합니다.
점수
코드·사람·모델이 매긴 값. 가능하면 이진 판정 + 근거가 좋습니다.

골든셋은 이렇게 만듭니다

  1. 실제 사례 20개를 모읍니다. 내가 직접 채점했던 응답, 검수를 통과한 문항, 실제로 틀렸던 사례. 손으로 만든 20개가 합성 200개보다 낫습니다.
  2. 경계 사례를 일부러 넣습니다. “거의 맞지만 핵심어가 빠진 답”, “표현은 다른데 의미가 같은 답”, “교육과정에 없는 개념을 섞은 답”.
  3. 합성으로 늘립니다. 아래 프롬프트로 변형을 만들되, 정답 라벨은 사람이 확인합니다.
  4. 버전을 붙입니다. evals/grade_v1.jsonl. 문제집을 바꾸면 점수를 비교할 수 없으므로, 셋은 되도록 고정하고 추가만 합니다.
<task>
아래 <item>과 <rubric>을 보고, 학생 응답 예시를 만들어라.
각 예시는 채점 결과가 서로 다르게 나오도록, 다음 유형을 하나씩 포함하라.
  1) 완전 정답
  2) 핵심 요소 하나 누락
  3) 표현은 다르지만 의미가 같은 정답
  4) 교육과정에 없는 개념을 섞은 답
  5) 문항이 묻지 않은 내용으로 분량을 채운 답
</task>

<output_format>
<examples> 안에 각각 <example type="..."><response>…</response>
<expected>요소별 충족/미충족 예상</expected></example>
</output_format>

<rules>
- 응답은 실제 학생이 쓸 법한 말투로 쓴다(교과서 문장 금지).
- 각 응답은 3~6문장.
- 정답을 그대로 베낀 응답은 만들지 않는다.
</rules>
합성 데이터의 함정

모델이 만든 응답은 모델이 좋아하는 모양입니다. 그래서 실제 학생 응답보다 채점이 쉽습니다. 합성 데이터로만 평가하면 점수가 실제보다 높게 나옵니다. 반드시 실제 응답 최소 10개를 섞으세요. 그리고 합성 데이터로 프롬프트를 튜닝하면 그 데이터에 과적합됩니다. 튜닝용과 검증용을 나누는 것이 원칙입니다.

4.3 채점 3방식: 코드 · 사람 · 모델

방식속도비용정확도적합한 작업
코드 기반즉시0규칙이 맞으면 100%형식 검사, 키 존재, 금칙어, 숫자 일치
사람느림비쌈기준최종 확인, judge 검증용 표본
모델(judge)빠름호출당루브릭이 좋으면 높음의미 판정, 루브릭 채점

핵심 원칙은 “가능하면 코드, 필요하면 모델, 최소한 사람”입니다. 코드로 잡을 수 있는 것을 모델에게 물으면 돈과 재현성을 동시에 잃습니다. 예를 들어 “JSON에 score 키가 있는가”는 코드가 100% 정확하게 봅니다. 

def code_checks(output: dict, schema: dict) -> list[str]:
    """모델 판정 없이 잡을 수 있는 것을 먼저 잡는다."""
    problems = []
    for key in schema.get("required", []):
        if key not in output or output[key] in (None, "", []):
            problems.append(f"필수 키 누락: {key}")
    if "score" in output:
        s = output["score"]
        if not isinstance(s, int) or not (0 <= s <= 10):
            problems.append(f"score 범위 위반: {s}")
    if "rationale" in output and len(str(output["rationale"])) < 10:
        problems.append("근거가 너무 짧음")
    return problems

이렇게 코드 검사로 먼저 걸러내고, 통과한 것만 모델 judge에게 보냅니다. 그러면 judge 호출이 줄고, judge의 오류가 우리 시스템 오류로 둔갑하지 않습니다.

4.4 judge 프롬프트 설계 7원칙

judge는 “채점하는 모델”입니다. 잘 쓰면 사람과 80~90% 일치하고, 못 쓰면 동전 던지기보다 조금 나은 정도입니다. 차이는 거의 전부 프롬프트 설계에서 납니다.

  1. 루브릭을 먼저 준다. “좋은 답인가?”를 묻지 말고 “이 조건을 충족했는가?”를 묻습니다.
  2. 이진 판정 + 근거. 참/거짓과 한 문장 근거를 함께 받습니다. 점수는 코드가 계산합니다.
  3. 근거를 먼저, 판정을 나중에. <thinking>에 인용·검토를 쓰고 <met>을 뒤에 둡니다.
  4. 판정 기준의 경계를 예시로 못 박는다. “표현이 달라도 의미가 같으면 충족” 같은 문장이 필수입니다.
  5. 모르는 것에 출구를 준다. “판정 불가”를 허용합니다. 억지 판정이 더 해롭습니다.
  6. 온도 0, 그리고 응답 파싱 실패 처리. 파싱 실패를 조용히 0점으로 만들지 마세요 — 오류로 남겨야 합니다.
  7. judge와 피평가자를 분리한다. 채점 대상 텍스트를 태그로 격리하고(프롬프트 인젝션 방지), 가능하면 다른 모델 계열을 씁니다.
judge의 세 가지 편향
  • 위치 편향 — A/B를 나란히 주면 앞쪽을 선호하는 경향. 순서를 바꿔 두 번 물어 평균을 냅니다.
  • 길이 편향 — 긴 답을 더 좋게 봅니다. “분량은 평가 요소가 아니다”를 명시합니다.
  • 자기 선호 — 자기 계열 모델의 문체를 좋아합니다. 가능하면 다른 모델로 채점하거나, 채점 기준을 문체가 아닌 내용에 묶습니다.

4.5 judge 코드: XML · 재시도 · 온도

judge 호출은 실패를 정상으로 가정하고 짜야 합니다. 태그가 빠지고, 앞에 설명이 붙고, 가끔 빈 응답이 옵니다. 그때 0점을 주면 시스템 오류가 학생 점수가 됩니다. 반드시 구분하세요. 

import json, re, time

JUDGE_SYSTEM = """당신은 채점 결과를 검토하는 평가자입니다.
- 주어진 채점 기준(rubric)만 사용합니다. 새로운 기준을 만들지 않습니다.
- 응답에 없는 내용을 추정해 충족으로 처리하지 않습니다.
- 판정이 불가능하면 <met>unknown</met> 을 씁니다.
- 출력은 지정된 XML 태그만 사용합니다."""

def judge_once(prompt: str, retries: int = 2) -> dict:
    last_err = None
    for attempt in range(retries + 1):
        try:
            resp = client.messages.create(
                model=MODEL, max_tokens=1200, temperature=0,
                system=JUDGE_SYSTEM,
                messages=[{"role": "user", "content": prompt}],
            )
            raw = "".join(b.text for b in resp.content if b.type == "text")
            parsed = parse_judge(raw)
            if parsed["ok"]:
                return parsed
            last_err = f"태그 없음(시도 {attempt+1}): {raw[:120]}"
        except Exception as e:                       # 네트워크·레이트리밋
            last_err = repr(e)
            time.sleep(2 ** attempt)                  # 지수 백오프
    return {"ok": False, "error": last_err}

def parse_judge(raw: str) -> dict:
    met = re.findall(r'<criterion id="(\w+)">\s*<met>(true|false|unknown)</met>', raw)
    if not met:
        return {"ok": False}
    return {
        "ok": True,
        "met": {cid: val for cid, val in met},
        "rationale": (re.search(r"<rationale>(.*?)</rationale>", raw, re.S) or [None, ""])[1].strip(),
        "raw": raw,
    }
unknown을 꼭 세세요

unknown 비율이 10%를 넘으면 루브릭이 모호하다는 신호입니다. “이 요소가 응답에 있는지 판단할 수 없다”는 것은 기준이 판정 가능하게 쓰이지 않았다는 뜻입니다. unknown을 버리지 말고 세어 보세요. 가장 값진 디버그 정보입니다.

4.6 우리 도메인: 서술형 루브릭 채점

이제 실제 서술형 문항에 붙입니다. 좋은 루브릭은 “읽는 사람이 판정할 수 있는 문장”으로 되어 있습니다. “잘 서술했다”는 판정 불가이고, “채집한 잎을 손상하지 않도록 다루는 태도를 언급했다”는 판정 가능합니다.

루브릭 작성 5원칙

  1. 한 요소에 한 판정. “정확히 지목하고 근거도 제시했다”는 두 요소로 쪼갭니다.
  2. 응답에서 관찰 가능한 것만. “이해했다”가 아니라 “~라고 썼다”.
  3. 부정 기준은 별도 축으로. 감점 요인(오개념·문항 밖 서술)은 요소 배점을 깎지 말고 따로 기록합니다.
  4. 배점은 사람이 정합니다. 모델에게 “이 요소는 몇 점이 적당한가”를 묻지 마세요.
  5. 버전과 해시를 남깁니다. 루브릭이 바뀌면 이전 점수와 비교할 수 없습니다.

def rubric_hash(rubric: dict) -> str:
    payload = json.dumps(rubric, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()[:12]
💡 2차(논술·면접)로 확장할 때

구조는 그대로 쓰되 축을 바꿉니다. 1차 서술형은 “요소 포함 여부”가 중심이지만, 2차 논술은 논리 전개·근거의 적절성·교육적 관점이 중심입니다. 이때도 원칙은 같습니다 — “논리적이다” 대신 “주장 → 근거 → 적용의 순서로 단락이 구성되었다”, “근거가 교육과정 성취기준과 연결되었다”처럼 관찰 가능한 문장으로 바꿉니다. 루브릭 문장을 다듬는 데 시간을 쓰는 것이, judge 모델을 바꾸는 것보다 거의 항상 더 큰 효과를 냅니다.

채점자 흔들림(rater drift) 점검

같은 답을 두 번 채점했을 때 결과가 달라지면, 그 채점기는 쓸 수 없습니다. 같은 20건을 두 번 돌려 일치율을 확인하는 것이 가장 싼 검사입니다. 

def self_consistency(prompt_builder, items: list[dict], rubric: dict, runs: int = 2) -> float:
    """같은 문항·응답을 여러 번 채점해 요소 판정이 일치하는 비율."""
    stable = total = 0
    for item in items:
        verdicts = []
        for _ in range(runs):
            parsed = judge_once(prompt_builder(item, rubric))
            verdicts.append(parsed.get("met", {}))
        keys = set().union(*[set(v) for v in verdicts]) if verdicts else set()
        for k in keys:
            values = {v.get(k) for v in verdicts}
            total += 1
            if len(values) == 1:
                stable += 1
    return stable / max(1, total)

0.9 이상이면 안정적입니다. 0.8 아래라면 대개 원인이 셋입니다 — 루브릭이 모호함, 응답이 아주 짧음, unknown을 너무 많이 냄. 앞의 둘은 루브릭으로, 마지막은 프롬프트로 고칩니다.

4.7 다축 채점과 부분점수

한 숫자로 채점하면 해석이 안 됩니다. “7점”이 내용이 좋아서인지 형식이 좋아서인지 알 수 없습니다. 그래서 축을 나누고, 축별 점수를 코드로 합산합니다. 

AXES = {
    "content": {"label": "내용 정확성", "weight": 0.5},
    "evidence": {"label": "근거 제시", "weight": 0.3},
    "structure": {"label": "구성·표현", "weight": 0.2},
}

def axes_to_score(axis_ratios: dict[str, float], max_score: int = 10) -> float:
    """axis_ratios: 축별 충족 비율(0~1). 가중합 → 점수."""
    total_w = sum(a["weight"] for a in AXES.values())
    ratio = sum(AXES[k]["weight"] * axis_ratios.get(k, 0.0) for k in AXES) / total_w
    return round(ratio * max_score, 1)


def summarize_axes(results: list[dict]) -> dict:
    """여러 응답을 축별로 집계 — 어디가 약한지 보인다."""
    out = {}
    for key, a in AXES.items():
        vals = [r["axes"].get(key, 0.0) for r in results if key in r.get("axes", {})]
        out[key] = {
            "label": a["label"],
            "avg": round(sum(vals) / len(vals), 3) if vals else None,
            "n": len(vals),
        }
    return out

4.8 사람 채점과의 일치도 (카파)

judge가 사람과 “얼마나 같은 판단을 하는가”를 재는 표준 지표가 Cohen’s kappa입니다. 단순 일치율은 우연히 맞는 경우를 세지 않기 때문에 부풀려집니다. 카파는 우연 일치를 빼고 계산합니다. 

import numpy as np

def cohen_kappa(human: list[str], model: list[str]) -> dict:
    """human/model: 같은 길이의 라벨 리스트. 이진 또는 다범주 모두 가능."""
    assert len(human) == len(model), "라벨 수가 다릅니다"
    labels = sorted(set(human) | set(model))
    n = len(human)
    idx = {lab: i for i, lab in enumerate(labels)}
    m = np.zeros((len(labels), len(labels)), dtype=int)
    for h, g in zip(human, model):
        m[idx[h], idx[g]] += 1

    po = np.trace(m) / n                                   # 관측 일치율
    row = m.sum(axis=1) / n
    col = m.sum(axis=0) / n
    pe = float((row * col).sum())                          # 우연 일치율
    kappa = (po - pe) / (1 - pe) if pe < 1 else 0.0

    # 라벨별 일치 (주로 'true' 쪽이 중요)
    per_label = {}
    for lab in labels:
        i = idx[lab]
        tp = m[i, i]
        per_label[lab] = round(tp / max(1, m[i, :].sum()), 3)
    return {"n": n, "observed_agreement": round(float(po), 3),
            "expected_agreement": round(pe, 3), "kappa": round(float(kappa), 3),
            "per_label_recall": per_label, "matrix": m.tolist(), "labels": labels}

import hashlib

def dedupe_jobs(rows: list[dict]) -> tuple[list[dict], dict[str, list[str]]]:
    """(문항 id, 응답 텍스트) 해시가 같으면 한 번만 채점하고 나중에 결과를 복사한다."""
    unique, groups = [], {}
    for r in rows:
        key = hashlib.sha256(f"{r['item_id']}::{r['response']}".encode()).hexdigest()[:16]
        groups.setdefault(key, []).append(r["id"])
        if len(groups[key]) == 1:
            unique.append({**r, "id": key})
    return unique, groups

def fanout_results(unique_results: list[dict], groups: dict[str, list[str]]) -> list[dict]:
    by_key = {r["id"]: r for r in unique_results}
    out = []
    for key, ids in groups.items():
        base = by_key.get(key)
        if not base:
            continue
        for original_id in ids:
            out.append({**base, "id": original_id})
    return out

4.12 eval 결과를 읽는 법

마지막으로 숫자를 읽는 법입니다. 여기서 실수하면 우연을 개선으로 착각합니다.

20문항짜리 평가셋에서 정확도가 80%에서 85%로 올랐다면, 그건 문항 하나가 바뀐 것입니다. 표본이 작으면 신뢰구간이 넓습니다. 대략 이렇게 계산합니다. 

import math

def wilson_interval(success: int, n: int, z: float = 1.96) -> tuple[float, float]:
    """비율의 95% 신뢰구간 (윌슨). 작은 표본에서도 그럴듯하게 동작한다."""
    if n == 0:
        return (0.0, 1.0)
    p = success / n
    denom = 1 + z**2 / n
    center = (p + z**2 / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z**2 / (4 * n**2)) / denom
    return (round(max(0, center - half), 3), round(min(1, center + half), 3))

for n in (20, 50, 100, 400):
    lo, hi = wilson_interval(int(n * 0.8), n)
    print(f"n={n:4d}  80%  →  95% CI [{lo:.2f}, {hi:.2f}]  폭 {hi-lo:.2f}")
n=  20  80%  →  95% CI [0.58, 0.92]  폭 0.34
n=  50  80%  →  95% CI [0.67, 0.89]  폭 0.22
n= 100  80%  →  95% CI [0.71, 0.87]  폭 0.16
n= 400  80%  →  95% CI [0.76, 0.84]  폭 0.08

n=20에서 80%는 “58%일 수도 92%일 수도 있다”는 뜻입니다. 그래서 20문항에서는 5%p 차이를 믿으면 안 됩니다. 판단 기준을 이렇게 잡으세요.

  • 20문항 — “완전히 망가졌는지”만 본다. 60% 아래로 떨어지면 즉시 롤백.
  • 50~100문항 — 10%p 이상 차이는 의미 있다.
  • 400문항 이상 — 4~5%p 차이도 읽을 수 있다.

평균보다 중요한 것: 불일치 사례

mean_score가 0.3점 올랐다는 사실보다, 어떤 항목이 여전히 틀리는지가 중요합니다. 결과 JSON에서 delta가 가장 큰(절댓값) 5건을 뽑아 읽으세요. 원인이 대개 반복됩니다 — 특정 유형, 특정 길이, 특정 과목. 그 하나를 고치면 평균이 3점 오르기도 합니다.

4.12. n=20에서 95% 구간 폭은 30%p를 넘습니다. 문항 하나가 바뀐 것과 구분되지 않습니다.

4.5 · 4.6. unknown은 “기준이 모호하다”는 신호입니다. 버리지 말고 세어서 루브릭을 고치세요.

실습 과제

  1. 골든셋 20건 만들기. 실제 응답 10건 + 합성 10건. 각 건에 요소별 기대 판정을 손으로 붙이세요. 이 작업이 이 모듈에서 가장 오래 걸리고 가장 값어치 있습니다.
  2. 카파 한 번 재기. 20건을 사람이 채점한 결과와 judge 결과로 cohen_kappa()를 돌려 보세요. 0.6이 안 나오면 불일치 3건을 골라 루브릭을 고치고 다시 재세요. 두 번째 숫자가 첫 번째보다 의미 있습니다.
  3. 회귀 테스트 자동화. 프롬프트 파일을 prompts/로 옮기고, 바뀌면 run_eval()이 돌아 evals/results/에 기록되게 하세요. 이 기록이 앞으로의 모든 판단 근거가 됩니다.
