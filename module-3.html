8,000문항 RAG 파이프라인

“내 자료를 보고 답하는 AI”를 만드는 일입니다. 청킹에서 시작해 임베딩·하이브리드 검색·리랭킹까지, 코랩 무료 GPU에서 실제로 돌아가는 한 벌을 끝까지 조립합니다.

16레슨 약 150분 선행: 모듈 1~2 근거: claude-cookbooks RAG · awesome-llm-apps
RAG를 한 문장으로

질문이 들어오면, 관련 있는 자료 조각을 먼저 찾아 프롬프트에 넣고, 그 자료만 근거로 답하게 하는 것. 그래서 성능은 두 곳에서 갈립니다 — 찾기(검색)와 읽기(프롬프트). 이 모듈은 그 둘을 따로 만듭니다. 섞어서 만들면 어디가 문제인지 영원히 모릅니다.

3.1 RAG가 답인 경우와 아닌 경우

요즘 모델은 문맥을 아주 길게 넣을 수 있습니다. 그러면 “전부 다 넣으면 되지 않나?” 하는 생각이 듭니다. 실제로 8천 문항 전체를 한 번에 넣는 것은 불가능합니다 — 토큰이 수백만 개가 되고, 비용과 지연이 감당이 안 되며, 무엇보다 긴 문맥 가운데 필요한 부분을 놓치는 현상이 생깁니다.

상황선택이유
자료가 한 문서(20~50쪽)이고 늘 같은 자료긴 문맥에 통째로검색 단계가 없어 실패 지점이 하나 줄어든다
자료가 수천 문서, 질문마다 다른 부분이 필요RAG비용·지연·정확도 모두 유리
“내 말투로 써 줘” 같은 스타일 학습파인튜닝검색으로 안 되는 것은 검색으로 안 된다
자료가 매일 바뀜RAG인덱스만 갱신하면 된다. 재학습 불필요
답이 자료 “밖”의 최신 사실웹 검색 / 도구RAG는 내 자료에만 충실하다

우리 상황은 두 번째 줄에 정확히 해당합니다. 문항 8천 개, 교육과정 노트 수백 개, 질문은 “이 개념이 나온 기출 찾아줘”, “이 성취기준과 연결된 문항 모아줘”처럼 매번 다른 부분을 건드립니다.

💡 사실 이 파이프라인은 세 가지 일을 동시에 합니다
  • 검색 — “이 개념 관련 문항” 찾기 (사람이 쓰는 검색)
  • 근거 제공 — 변형문제 생성 시 원문·해설을 붙여 주기 (모듈 1의 프롬프트에 넣을 재료)
  • 중복 감지 — 새로 만든 문항이 기존 8천 개와 너무 비슷한지 확인

세 번째가 특히 값어치가 큽니다. 임베딩이 이미 있으면 중복 판정은 거의 공짜입니다.

3.2 8천 문항의 구조를 먼저 그린다

청킹은 “글을 자르는 기술”이 아니라 “검색 단위를 정하는 결정”입니다. 그러니 코드보다 먼저 내 자료에서 무엇이 한 단위인가를 정해야 합니다. imgo-node에는 이미 단위가 있습니다.

청크 단위크기(대략)잘 맞는 질문약점
문항 1개 (파일 1개)300~1,200자“이런 문항 있어?”, “비슷한 기출 찾아줘”긴 제시문은 잘리기도
교육과정 노드 (파일 1개)1,000~6,000자“이 개념 설명해줘”, “성취기준 뭐야”너무 길면 임베딩이 흐려짐
회독표 한 행40~120자“평가 절차 5단계가 뭐였지”맥락이 없어 단독으로는 약함
해설 단락200~600자“왜 이게 정답이야”문항 없이는 의미가 반쪽

정답은 섞는 것입니다. 단, 섞을 때도 각 청크에 “무엇의 일부인지”를 메타데이터로 붙입니다. 그래야 검색 결과를 원문 전체로 되돌릴 수 있습니다(이걸 small-to-big 전략이라 부릅니다).

3.3 청킹: 무엇을 한 덩어리로 볼 것인가

가장 흔한 실수는 고정 길이로 자르는 것입니다. 500자씩 자르면 문항 중간에서 잘리고, 정답이 다음 청크로 넘어갑니다. 우리 자료는 이미 ##로 구조가 잡혀 있으니 구조를 따라 자르면 됩니다. 

import re
from pathlib import Path

SECTION_RE = re.compile(r"^##\s+(.+?)\s*$", re.M)


def split_sections(md_body: str) -> list[tuple[str, str]]:
    """'## 제목' 기준으로 (제목, 본문) 목록을 만든다. 첫 제목 앞부분은 preamble."""
    marks = list(SECTION_RE.finditer(md_body))
    if not marks:
        return [("", md_body.strip())]
    out = []
    head = md_body[: marks[0].start()].strip()
    if head:
        out.append(("", head))
    for i, m in enumerate(marks):
        end = marks[i + 1].start() if i + 1 < len(marks) else len(md_body)
        out.append((m.group(1).strip(), md_body[m.end():end].strip()))
    return out


def build_question_chunks(doc_id: str, meta: dict, body: str, path: str) -> list[dict]:
    """문항 1개 → 청크 1~2개(발문 / 해설). 각 청크 앞에 맥락 헤더를 붙인다."""
    secs = split_sections(body)

    def pick(*keys: str) -> str:
        for heading, text in secs:
            if any(k in heading for k in keys):
                return text
        return ""

    stem = pick("문제 본문", "문항", "문제")
    answer = pick("정답", "답안")
    expl = pick("해설", "풀이")

    base = {
        "subject": meta.get("subject", ""),
        "year": meta.get("year"),
        "question_type": meta.get("question_type", ""),
        "primary_node": meta.get("primary_node", ""),
        "node_title": meta.get("node_title", ""),
        "source_path": path,
    }
    chunks = []

    if stem:
        header = f"[{base['subject']} {base['year']} {meta.get('question', '')}번 · {base['node_title']}]"
        chunks.append({
            "chunk_id": f"q:{doc_id}",
            "doc_id": doc_id,
            "kind": "question",
            "text": header + "\n" + stem,
            "meta": {**base, "heading": "문제 본문"},
        })

    if expl:
        header = f"[{base['subject']} {base['year']} {meta.get('question', '')}번 해설]"
        chunks.append({
            "chunk_id": f"e:{doc_id}",
            "doc_id": doc_id,
            "kind": "explanation",
            "text": header + "\n" + expl,
            "meta": {**base, "heading": "해설", "answer_preview": answer[:80]},
        })

    return chunks
“맥락 헤더”를 꼭 붙이세요

[과학 2019 5번 · 과학 탐구] 같은 한 줄이 검색 품질을 눈에 띄게 올립니다. 청크만 떼어 놓으면 “이게 무엇에 관한 글인지” 정보가 사라지기 때문입니다. 비용은 청크당 15토큰 수준입니다. 같은 원리로, 교육과정 표 행에는 표 제목과 과목을 앞에 붙입니다.

교육과정 노트는 조금 다르게 자릅니다. 절이 길면 문단 경계에서 나누고 앞부분을 조금 겹쳐 줍니다.

def chunk_curriculum(doc_id: str, meta: dict, body: str, path: str,
                     max_chars: int = 1200, overlap: int = 120) -> list[dict]:
    """교육과정: ## 절 단위 → 너무 길면 max_chars로 나누되 overlap만큼 겹친다."""
    out = []
    for i, (heading, text) in enumerate(split_sections(body)):
        if not text:
            continue
        if len(text) <= max_chars:
            pieces = [text]
        else:
            step = max_chars - overlap
            pieces = [text[j:j + max_chars] for j in range(0, len(text), step)]

        for k, piece in enumerate(pieces):
            out.append({
                "chunk_id": f"c:{doc_id}#{i}-{k}",
                "doc_id": doc_id,
                "kind": "curriculum",
                "text": f"[{meta.get('subject','')} · {heading or '본문'}]\n{piece}",
                "meta": {
                    "subject": meta.get("subject", ""),
                    "primary_node": meta.get("id", ""),
                    "node_title": heading or meta.get("id", ""),
                    "status": "verified" if str(meta.get("canonical")).lower() == "true" else "review",
                    "source_path": path,
                    "heading": heading,
                },
            })
    return out
overlap은 만능이 아닙니다

겹침(overlap)은 “문장이 경계에서 끊겨 의미가 사라지는” 문제를 줄여 주지만, 중복 결과도 만듭니다. 같은 내용이 두 청크에 들어가면 검색 결과 상위가 같은 문서로 도배됩니다. 우리처럼 절 단위 구조가 뚜렷한 자료에서는 overlap 0~10%로 충분하고, 리랭킹 단계에서 doc_id 기준 중복 제거를 하는 편이 깔끔합니다.

3.4 임베딩: 문장을 좌표로

임베딩은 텍스트를 의미가 가까우면 가까운 좌표로 바꾸는 일입니다. “교수·학습 방법”과 “수업 모형”은 가까이 있고, “평가 절차”는 조금 멀어집니다. 이 좌표들 사이의 거리로 검색합니다.

한국어 + 무료 + 코랩 GPU 조합에서 가장 무난한 출발점은 BAAI/bge-m3입니다.

모델차원특징추천 상황
BAAI/bge-m31024다국어·긴 입력·한국어 강함기본 선택. 청크가 길어도 된다
nlpai-lab/KURE-v11024한국어 검색 특화한국어만 다루고 정확도를 더 조이고 싶을 때
jhgan/ko-sroberta-multitask768가볍고 빠름속도 우선, 짧은 문장 위주
 
# !pip install -q sentence-transformers
import numpy as np
import torch
from sentence_transformers import SentenceTransformer

DEVICE = "cuda" if torch.cuda.is_available() else "cpu"
model = SentenceTransformer("BAAI/bge-m3", device=DEVICE)
model.max_seq_length = 512        # 청크 길이에 맞춰 조절 — 길수록 느려진다


def embed_texts(texts: list[str], batch_size: int = 16) -> np.ndarray:
    """정규화된 임베딩. 정규화하면 내적(dot)이 곧 코사인 유사도가 된다."""
    vecs = model.encode(
        texts,
        batch_size=batch_size,
        normalize_embeddings=True,
        show_progress_bar=True,
        convert_to_numpy=True,
    )
    return vecs.astype("float32")

normalize_embeddings=True가 핵심입니다. 정규화해 두면 유사도 계산이 내적 한 번(@)으로 끝나고, faiss의 IndexFlatIP를 그대로 쓸 수 있습니다. 정규화를 빼면 “코사인 유사도”와 “내적”이 달라져 순위가 어긋납니다.

코랩 무료 GPU에서 8천 청크 현실 점검
  • bge-m3(약 5.6억 파라미터)로 1,000청크당 3~6분 정도가 무난한 기대치입니다(배치 16, T4).
  • 메모리가 터지면 batch_size를 8, 그래도 안 되면 4로. 청크를 줄이는 것보다 배치를 줄이는 게 먼저입니다.
  • 한 번 계산하고 저장하세요. .npy로 저장하면 다음 세션은 로드만 합니다. 무료 런타임은 세션이 끊기면 다 사라집니다.
  • 드라이브에 저장하면 세션이 끊겨도 살아남습니다. 임베딩은 인덱스와 같은 폴더에 두세요.

3.5 벡터 인덱스 만들기

8천 개는 사실 인덱스 없이도 됩니다. 8,000 × 1,024 행렬에 질문 벡터를 곱하면 800만 번의 곱셈이고, CPU에서도 수십 ms입니다. 그래서 처음에는 numpy로 시작하고, 5만 개를 넘어가면 faiss로 옮기는 것이 합리적입니다. 필요해지기 전에 복잡하게 만들지 마세요. 

import json
import os
import numpy as np


class NumpyIndex:
    """8천~3만 청크 규모에서 충분한 초경량 인덱스."""

    def __init__(self, dim: int = 1024):
        self.vecs = np.zeros((0, dim), dtype="float32")
        self.chunks: list[dict] = []

    def add(self, vecs: np.ndarray, chunks: list[dict]) -> None:
        assert len(vecs) == len(chunks), "벡터와 청크 수가 다릅니다"
        self.vecs = np.vstack([self.vecs, vecs]) if len(self.vecs) else vecs
        self.chunks.extend(chunks)

    def search_dense(self, qvec: np.ndarray, k: int = 10, mask: np.ndarray | None = None):
        sims = self.vecs @ qvec                       # 이미 정규화 → 코사인
        if mask is not None:
            sims = np.where(mask, sims, -1.0)
        k = min(k, len(sims))
        idx = np.argpartition(-sims, k - 1)[:k]
        idx = idx[np.argsort(-sims[idx])]
        return [(int(i), float(sims[i]), self.chunks[i]) for i in idx]

    def save(self, folder: str) -> None:
        os.makedirs(folder, exist_ok=True)
        np.save(f"{folder}/vectors.npy", self.vecs)
        with open(f"{folder}/chunks.json", "w", encoding="utf-8") as f:
            json.dump(self.chunks, f, ensure_ascii=False)

    @classmethod
    def load(cls, folder: str) -> "NumpyIndex":
        obj = cls()
        obj.vecs = np.load(f"{folder}/vectors.npy")
        with open(f"{folder}/chunks.json", encoding="utf-8") as f:
            obj.chunks = json.load(f)
        return obj

규모가 커지면 같은 인터페이스로 faiss를 끼웁니다. 나머지 코드는 바뀌지 않습니다.

# !pip install -q faiss-cpu
import faiss


class FaissIndex:
    def __init__(self, dim: int = 1024):
        self.index = faiss.IndexFlatIP(dim)       # 정규화된 벡터의 내적 = 코사인
        self.chunks: list[dict] = []

    def add(self, vecs: np.ndarray, chunks: list[dict]) -> None:
        self.index.add(vecs)
        self.chunks.extend(chunks)

    def search_dense(self, qvec: np.ndarray, k: int = 10):
        scores, ids = self.index.search(qvec.reshape(1, -1).astype("float32"), k)
        return [(int(i), float(s), self.chunks[int(i)])
                for i, s in zip(ids[0], scores[0]) if i != -1]

    def save(self, folder: str) -> None:
        faiss.write_index(self.index, f"{folder}/faiss.index")
        with open(f"{folder}/chunks.json", "w", encoding="utf-8") as f:
            json.dump(self.chunks, f, ensure_ascii=False)
“몇 개부터 faiss?” 감각

numpy 검색은 1만 청크까지 수십 ms, 10만 청크에서 0.5초 안팎을 기대할 수 있습니다. 대화형이라면 1만까지는 numpy로 충분합니다. 병목은 검색이 아니라 모델 호출이라는 점도 기억하세요 — 검색을 100ms 줄여도 생성이 5초면 체감되지 않습니다.

3.6 1단계 검색: dense top-k와 임계값

질문을 임베딩해 가장 가까운 k개를 꺼냅니다. 여기서 결정할 것이 셋입니다. k, 임계값, 그리고 결과가 없을 때의 행동입니다. 

def dense_search(index, query: str, k: int = 8, min_score: float = 0.35):
    qvec = embed_texts([query])[0]
    hits = index.search_dense(qvec, k=k)
    return [(i, s, c) for i, s, c in hits if s >= min_score]

k빠르고 정밀하지만 정답을 놓칠 수 있음놓칠 확률↓, 잡음↑, 프롬프트 길어짐1차 8~20 → 리랭킹 후 3~5

임계값은 모델마다 다릅니다

0.35는 bge-m3 기준의 출발점일 뿐입니다. 모델을 바꾸면 점수 분포가 통째로 달라집니다. 그래서 임계값을 코드에 상수로 박지 말고, “정답이 있는 질문 20개 + 없는 질문 20개”로 분포를 그려 보고 정하세요. 정답 질문의 하위 점수와 오답 질문의 상위 점수 사이가 좋은 경계입니다. 이 작업이 3.12와 모듈 4로 이어집니다.

💡 “결과 없음”을 정상 동작으로 만드세요

검색 결과가 없거나 점수가 낮을 때 빈손으로 모델을 부르면, 모델은 일반 지식으로 답합니다. 그게 우리 자료 기반 시스템에서는 최악의 실패입니다. 임계값 미달이면 모델을 부르지 않고 “자료에서 찾지 못했습니다”라고 답하는 분기를 반드시 넣으세요. 모듈 1의 “출구 주기”를 시스템 수준에서 하는 것입니다.

3.7 2단계: BM25 하이브리드와 RRF

임베딩은 의미를 잡지만 정확한 문자열에는 약합니다. 학생이 “성취기준 해설의 ‘~은 다루지 않는다’ 부분” 처럼 특정 표현을 정확히 물으면, 의미 검색은 비슷한 다른 절을 물어옵니다. 이때 강한 것이 BM25(키워드 기반 고전 검색)입니다.

둘을 합치는 방법은 여러 가지인데, 가장 튼튼하고 손이 적게 가는 것이 RRF(Reciprocal Rank Fusion)입니다. 점수가 아니라 순위를 합칩니다. 그래서 서로 단위가 다른 두 검색기의 점수를 억지로 맞출 필요가 없습니다. 

RRF 점수(d) = Σ  1 / (k + rank_i(d))        k = 60 (관례값)

예) 어떤 청크가 dense에서 2위, BM25에서 7위라면
    1/(60+2) + 1/(60+7) = 0.01613 + 0.01493 = 0.03106
    두 검색기 모두 상위권이면 자연히 점수가 커진다

한국어는 띄어쓰기만으로 토큰을 나누면 조사가 붙어 버립니다. 형태소 분석기 kiwipiepy로 명사·동사를 뽑습니다.

# !pip install -q rank_bm25 kiwipiepy
from kiwipiepy import Kiwi
from rank_bm25 import BM25Okapi

kiwi = Kiwi()


def tokenize_ko(text: str) -> list[str]:
    """BM25용 토큰: 명사·동사·영문/숫자만. 조사·어미는 버린다."""
    out = []
    for t in kiwi.tokenize(text):
        if t.tag.startswith(("N", "V")) or t.tag in ("SL", "SN"):
            out.append(t.form.lower())
    return out


class BM25Retriever:
    def __init__(self, chunks: list[dict]):
        self.chunks = chunks
        self.corpus = [tokenize_ko(c["text"]) for c in chunks]
        self.bm25 = BM25Okapi(self.corpus)

    def search(self, query: str, k: int = 20):
        scores = self.bm25.get_scores(tokenize_ko(query))
        idx = scores.argsort()[::-1][:k]
        return [(int(i), float(scores[i]), self.chunks[int(i)]) for i in idx if scores[i] > 0]


def rrf_merge(result_lists: list[list[tuple]], k: int = 60, top_n: int = 8):
    """여러 검색 결과(각각 (idx, score, chunk))를 순위 기준으로 합친다."""
    fused: dict[int, dict] = {}
    for results in result_lists:
        for rank, (idx, score, chunk) in enumerate(results, start=1):
            slot = fused.setdefault(idx, {"idx": idx, "chunk": chunk, "rrf": 0.0, "ranks": []})
            slot["rrf"] += 1.0 / (k + rank)
            slot["ranks"].append(rank)
    ordered = sorted(fused.values(), key=lambda d: -d["rrf"])[:top_n]
    return [(d["idx"], d["rrf"], d["chunk"]) for d in ordered]

두 검색기를 합치면 코드는 이렇게 됩니다. 여기서 1차 후보를 넉넉히(20~40개) 뽑는 것이 중요합니다. 리랭커에게 선택지를 줘야 합니다.

def hybrid_search(query: str, dense_idx, bm25: BM25Retriever,
                  k_dense: int = 20, k_bm25: int = 20, top_n: int = 20):
    qvec = embed_texts([query])[0]
    d = dense_idx.search_dense(qvec, k=k_dense)
    b = bm25.search(query, k=k_bm25)
    return rrf_merge([d, b], top_n=top_n)

3.8 메타데이터 필터 설계

“2022년 과학 기출 중 서술형”에서 “2022년 과학 서술형”은 검색 조건이고, 나머지가 의미입니다. 조건을 임베딩에 맡기면 안 됩니다. 어휘가 아니라 속성이기 때문입니다.

방식어떻게장점단점
사전 필터(pre-filter)검색 전에 후보를 줄인다빠르고, 조건이 반드시 지켜진다후보가 너무 적으면 결과가 빈약
사후 필터(post-filter)상위 k를 뽑은 뒤 조건에 맞는 것만 남긴다의미 검색의 폭을 유지조건이 희귀하면 결과가 0개가 되기 쉽다

실무 해법은 사전 필터 + 후보 수 늘리기입니다. 필터를 걸었을 때는 k를 2~3배로 키워 “조건을 만족하는 좋은 후보”가 살아남을 여지를 만듭니다. 

import re

SUBJECTS = ["국어", "수학", "사회", "과학", "도덕", "실과", "체육", "음악", "미술", "영어", "통합교과"]
TYPES = ["서술형", "논술형", "선택형", "단답형"]


def parse_filters(query: str) -> dict:
    """질문에서 명시적 조건만 뽑는다. 못 찾으면 비워 둔다(추측 금지)."""
    f = {}
    for s in SUBJECTS:
        if s in query:
            f["subject"] = s
            break
    years = re.findall(r"(19|20)\d{2}", query)
    m = re.search(r"((?:19|20)\d{2})\s*년?", query)
    if m:
        f["year"] = int(m.group(1))
    for t in TYPES:
        if t in query:
            f["question_type"] = t
            break
    if "기출" in query:
        f["kind"] = "question"
    if "교육과정" in query or "성취기준" in query:
        f["kind"] = "curriculum"
    return f


def build_mask(chunks: list[dict], filters: dict) -> np.ndarray | None:
    if not filters:
        return None
    mask = np.ones(len(chunks), dtype=bool)
    for i, c in enumerate(chunks):
        m = c["meta"]
        for key, want in filters.items():
            if key == "kind":
                ok = c["kind"] == want
            elif key == "year":
                ok = str(m.get("year")) == str(want)
            else:
                ok = str(m.get(key, "")) == want
            if not ok:
                mask[i] = False
    return mask

3.9 Reranking: 순위를 다시 매긴다

하이브리드 검색은 “관련 있을 만한 후보 20개”를 뽑는 데 강하고, 정확한 순서를 정하는 데 약합니다. 리랭킹은 후보를 질문과 하나씩 나란히 놓고 다시 점수를 매깁니다. 이 단계에서 정확도가 가장 크게 오릅니다.

방식도구속도비용
cross-encoder (추천)BAAI/bge-reranker-v2-m3후보 20개에 1~2초(GPU)무료(로컬)
LLM 리랭킹Claude에게 순위만 받기1~3초호출당 과금
규칙 기반최신 연도 가중, status=verified 가중즉시무료
 
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3", device=DEVICE, max_length=512)


def rerank(query: str, candidates: list[tuple], top_k: int = 5):
    """candidates: [(idx, score, chunk)] → 상위 top_k 재정렬"""
    if not candidates:
        return []
    pairs = [(query, c["text"]) for _, _, c in candidates]
    scores = reranker.predict(pairs, batch_size=8)
    order = np.argsort(-scores)[:top_k]
    return [(candidates[i][0], float(scores[i]), candidates[i][2]) for i in order]

3.10 컨텍스트 조립과 생성 프롬프트

검색이 끝났으면 읽히게 만들어야 합니다. 여기서 흔한 실수는 문서를 그냥 이어 붙이는 것입니다. 모델은 어디까지가 한 문서인지, 어느 문서를 근거로 썼는지 알 수 없습니다. 태그로 감싸고 번호를 붙입니다. 

def build_context(hits: list[tuple], max_chars: int = 6000) -> str:
    parts, total = [], 0
    for n, (idx, score, c) in enumerate(hits, start=1):
        body = c["text"]
        if total + len(body) > max_chars:
            body = body[: max_chars - total]
        m = c["meta"]
        parts.append(
            f'<document id="{n}" subject="{m.get("subject","")}" year="{m.get("year","")}"'
            f' node="{m.get("primary_node","")}" kind="{c["kind"]}">\n{body}\n</document>'
        )
        total += len(body)
        if total >= max_chars:
            break
    return "\n\n".join(parts)

3.11 요약 인덱싱: 검색용 텍스트와 읽기용 텍스트를 나눈다

청크가 길면 임베딩이 여러 주제가 섞인 평균이 됩니다. “평가 절차”를 물었는데 그 절에 평가 방향·평가 방법·유의점이 다 들어 있으면, 벡터는 그 중간 어딘가를 가리킵니다. 이때 쓰는 것이 요약 인덱싱입니다. 청크마다 2~3문장 요약을 만들어, 요약을 임베딩하고 원문은 답변 근거로 씁니다. 

SUMMARY_MODEL = os.environ.get("SUMMARY_MODEL", "claude-haiku-5-5")

</task>

<content>
제목: {heading}
본문:
{text}
</content>

<rules>
- 머리말 없이 요약만 쓴다. "요약하면" 같은 표현 금지.
- 문서에 나온 용어를 그대로 쓴다(동의어로 바꾸지 않는다) — 검색이 어긋난다.
- 숫자·단계·목록은 생략하지 않는다.
- 결과는 <summary> 태그 안에만 쓴다.
</rules>"""


def summarize_chunk(chunk: dict) -> str:
    resp = client.messages.create(
        model=SUMMARY_MODEL, max_tokens=400, temperature=0,
        messages=[{"role": "user", "content": SUMMARY_PROMPT.format(
            heading=chunk["meta"].get("heading", ""), text=chunk["text"][:4000])}],
    )
    raw = "".join(b.text for b in resp.content if b.type == "text")
    m = re.search(r"<summary>(.*?)</summary>", raw, re.S)
    return (m.group(1) if m else raw).strip()


def with_summaries(chunks: list[dict], limit: int | None = None) -> list[dict]:
    out = []
    for i, c in enumerate(chunks):
        if limit and i >= limit:
            out.append(c)
            continue
        c = dict(c)
        c["summary"] = summarize_chunk(c)
        # 임베딩용 텍스트: 제목 + 요약 + 본문 앞부분
        c["embed_text"] = f"{c['meta'].get('heading','')}\n{c['summary']}\n{c['text'][:600]}"
        out.append(c)
    return out

3.12 검색 품질 측정

검색을 고칠 때마다 같은 질문으로 같은 숫자를 뽑아야 합니다. 필요한 지표는 네 개면 충분합니다.

지표의미언제 중요
Precision@k꺼낸 k개 중 정답 비율프롬프트가 길어지는 게 부담일 때
Recall@k정답 중 꺼낸 비율대부분 여기가 중요 — 놓치면 답이 불가능
MRR@k첫 정답이 몇 위에 나왔는지의 역수 평균상위 1~2개만 프롬프트에 넣을 때
E2E 정확도최종 답이 맞았는지(judge)정말 사용자가 만족하는지
 
import json
from statistics import mean


def precision_recall_mrr(results: list[tuple], gold_ids: set[str], k: int = 8):
    got = [c["doc_id"] for _, _, c in results[:k]]
    hit = len(set(got) & gold_ids)
    precision = hit / max(1, len(got))
    recall = hit / max(1, len(gold_ids))
    mrr = 0.0
    for rank, doc_id in enumerate(got, start=1):
        if doc_id in gold_ids:
            mrr = 1.0 / rank
            break
    return precision, recall, mrr


def evaluate(search_fn, eval_set: list[dict], k: int = 8, label: str = "") -> dict:
    """eval_set: [{"query": ..., "gold_doc_ids": ["과학_2019_05", ...]}, ...]"""
    ps, rs, ms = [], [], []
    misses = []
    for item in eval_set:
        res = search_fn(item["query"])
        p, r, m = precision_recall_mrr(res, set(item["gold_doc_ids"]), k=k)
        ps.append(p); rs.append(r); ms.append(m)
        if r == 0:
            misses.append(item["query"])
    report = {
        "label": label,
        "k": k,
        "n": len(eval_set),
        "precision": round(mean(ps), 3) if ps else 0,
        "recall": round(mean(rs), 3) if rs else 0,
        "mrr": round(mean(ms), 3) if ms else 0,
        "misses": misses,
    }
    f1 = 2 * report["precision"] * report["recall"] / max(1e-9, report["precision"] + report["recall"])
    report["f1"] = round(f1, 3)
    print(json.dumps(report, ensure_ascii=False, indent=2))
    return report

misses가 이 함수의 진짜 값입니다. 어떤 질문을 놓쳤는지 읽어 보면 원인이 대개 셋 중 하나입니다 — 청킹(정답이 두 청크로 찢어짐), 메타데이터(필터가 너무 좁음), 어휘(사용자 말과 자료 말이 다름). 숫자만 보면 알 수 없습니다.

3.14 운영: 증분 인덱싱 · 비용 · 갱신

인덱스는 한 번 만들고 끝이 아닙니다. 문항이 추가되고, 오탈자가 고쳐지고, 노드 매핑이 바뀝니다. 매번 8천 개를 다시 임베딩하면 시간도 아깝고, 무료 GPU 시간도 금방 바닥납니다. 해법은 바뀐 것만 처리하는 것입니다. 

import hashlib, json
from pathlib import Path

def file_hash(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()[:16]


def incremental_update(root: Path, index_dir: str):
    """문서 해시 매니페스트를 비교해 추가·변경된 청크만 임베딩한다."""
    manifest_path = Path(index_dir) / "manifest.json"
    manifest = json.loads(manifest_path.read_text()) if manifest_path.exists() else {}

    current: dict[str, dict] = {}
    for path in Path(root, "content").rglob("*.md"):
        if any(p.startswith("_") for p in path.relative_to(root).parts):
            continue
        h = file_hash(path)
        current[str(path)] = {"hash": h, "doc_id": path.stem}

    changed = [p for p, v in current.items() if manifest.get(p, {}).get("hash") != v["hash"]]
    removed = [p for p in manifest if p not in current]
    print(f"변경 {len(changed)} / 삭제 {len(removed)}")

    # 기존 인덱스 로드 → 삭제·변경분 제거 → 신규만 임베딩 → 병합
    idx = NumpyIndex.load(index_dir)
    keep = [i for i, c in enumerate(idx.chunks) if c["meta"].get("source_path") not in set(changed) | set(removed)]
    old_vecs = idx.vecs[keep]
    old_chunks = [idx.chunks[i] for i in keep]

    new_chunks = []
    for p in changed:
        meta, body = read_md(Path(p))
        kind = str(meta.get("node_kind", ""))
        if kind in ("qbank", "practice_mock_question"):
            new_chunks += build_question_chunks(Path(p).stem, meta, body, p)
        elif kind == "curriculum_doc":
            new_chunks += chunk_curriculum(Path(p).stem, meta, body, p)

    new_vecs = embed_texts([c["text"] for c in new_chunks]) if new_chunks else np.zeros((0, old_vecs.shape[1]), "float32")
    merged = NumpyIndex()
    merged.add(np.vstack([old_vecs, new_vecs]), old_chunks + new_chunks)
    merged.save(index_dir)

    manifest_path.write_text(json.dumps(current, ensure_ascii=False, indent=1))
    print("완료:", len(merged.chunks), "청크")
BM25는 다시 만들어야 합니다

BM25는 전체 문서의 단어 빈도에 의존하므로 전체 재계산이 필요합니다. 다만 형태소 분석만 하면 되므로 임베딩보다 훨씬 빠릅니다(8천 청크에 1~2분). “임베딩은 증분, BM25는 전체”가 현실적인 조합입니다.

증상가능한 원인확인 방법처방
항상 “자료에서 찾지 못했습니다” 임계값이 너무 높거나, 질문 임베딩이 청크와 다른 언어/스타일 상위 10개의 점수를 그대로 출력 임계값 0.30으로 낮춰 보기, 질문에 도메인 단어 붙이기
관련 없는 문항만 나옴 청크에 맥락 헤더가 없거나, 임베딩 모델이 한국어에 약함 검색된 청크의 text 앞부분을 눈으로 확인 맥락 헤더 추가, bge-m3 또는 KURE-v1로 교체
정답이 늘 3~4위 1차 검색은 맞는데 순위가 흐림 리랭킹 전후 MRR 비교 리랭커 도입 또는 가중치 조정
같은 문항의 청크가 상위를 도배 overlap 과다 또는 발문/해설이 따로 검색됨 상위 결과의 doc_id 중복 확인 doc_id 기준 중복 제거, overlap 축소
필터를 걸면 0건 메타데이터가 비었거나 타입 불일치(“2019” vs 2019) 해당 조건의 청크 수를 직접 세기 인덱싱 시 메타 정규화, 필터 비교를 문자열로
표 내용을 못 찾음 표가 이미지로만 있음(전처리 누락) 해당 문서의 청크 text에 표가 있는지 모듈 2의 표 추출·비전 파이프라인 재실행
답이 자료 밖 내용을 말함 검색 실패 후 모델이 일반 지식으로 답변 프롬프트에 빈 context가 들어갔는지 로그 확인 빈 결과면 모델 호출 자체를 건너뛰기
